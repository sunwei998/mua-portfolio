业界怎么做

图片慢、视频变形、点了没反应——成熟产品在这三件事上的通用解法，与我们的差距
2026-10-04  ·  纯研究稿，未修改任何项目代码
数据来源：腾讯云官方文档、Next.js 官方文档、MDN、web.dev、caniuse 口径的第三方汇总，以及本机对本项目素材的实测

Part 00一句话结论

成熟团队处理这三类问题，靠的是同一套分层配方：先让图片别从自己的应用服务器发出去，再让图片本身足够小、尺寸刚好、有占位、有优先级。我们的问题没有一处是特殊难题，全部落在标准答案里。

但对我们要额外加一条约束：配方里收益最大的第一层（对象存储 + CDN）需要已备案域名。腾讯云官方文档写明：2024 年 1 月 1 日后新建的存储桶，用默认域名访问会一律直接下载而不是预览，必须绑自定义域名；而国内 CDN 加速域名又要求备案。所以这条路不是不想走，是被备案卡住。在备案下来之前，唯一能动的杠杆是「字节数」和「加载顺序」。

Part 01图片：业界的五层配方

从上到下依次是「最高收益」到「最细打磨」。绝大部分站的性能问题，卡在第 2、3 层没做。

第 1 层 · 图不从应用服务器发最高收益我们：被备案卡住

把原图放进对象存储（COS / OSS / S3 / R2），由 CDN 边缘发出。字节数一项没变，但吞吐量从 0.5 MB/s 变成几百 MB/s，并且 URL 带处理参数就能实时转格式、裁尺寸。

腾讯云这一侧的原生能力（数据万象 CI）已经很完整，这也是我们项目早期定方案时就写好的路线：

https://bucket.cos.ap-xx.myqcloud.com/photo.jpg?imageMogr2/thumbnail/780x/format/webp/rquality/90
  • 处理结果由 CDN 缓存，同一 URL 二次命中不重复计费。
  • 腾讯云 COS 官方文档：中国大陆单账号单地域默认上行/下行各 15 Gbit/s，QPS 3 万；对比我们实测 532 KB/s，差三个数量级。
  • 还有「极智压缩」这类开关式能力：开通后访问图片即自动压缩，平均省一半体积，客户端完全不用改。
来源：腾讯云 COS《规格与限制》《域名管理概述》《基础图片处理》；关键限制见《上传与下载》——2024-01-01 后创建的桶，默认域名（含静态网站域名、全球加速域名）访问任意类型文件均不支持预览，只能通过已备案的自定义域名。
第 2 层 · 换现代格式最高收益我们：未做

业界标准是三层 <picture>：AVIF 优先 → WebP 兜底 → JPEG 最后兜底。浏览器按 type 挑第一个能解的，不支持自动降级，不需要任何 JS。

<picture>
  <source srcset="photo.avif" type="image/avif">
  <source srcset="photo.webp" type="image/webp">
  <img src="photo.jpg" width="1024" height="1536" alt="…">
</picture>

但对我们这个类目（微信分享是主要入口）建议只用两层：WebP + JPEG。理由是 AVIF 在微信场景不成立：

格式全球覆盖最早支持版本微信 / 国内场景
WebP约 96–97%Safari 14（2020）、Chrome 32X5 内核普遍支持
AVIF约 93–95%Safari 16.4（2023）、Chrome 85X5 基于旧 Chromium，支持率显著偏低

AVIF 的另一半代价是编码慢——同一张图 WebP 约 0.2–0.5 秒，AVIF 默认档 0.35 秒但换成高质量档可以到十几秒。对于「上传时批量处理」的流水线，这是一笔不划算的账。

来源：caniuse 口径第三方汇总（2026 上半年）；编码耗时来自 xconvert / pixconv 的实测对照。注：第三方博客给出的「微信场景 AVIF 低于 12%」这类具体数字可信度存疑，此处只采用方向性结论——AVIF 在国内移动端，尤其微信内置浏览器，覆盖明显差于 WebP。

一句话：AVIF 可以留作以后加，但现在不要为它增加任何流水线复杂度。WebP 是我们要的地。

第 3 层 · 分辨率分级（srcset / sizes）最高收益我们：未做  |  我上一份设计稿：漏掉了

这是成熟 site 和我们之间最明确的一条差距：我们每种资源只交付一种尺寸，列表缩略图和点开的大图是同一个文件。业界做法是按显示宽度分级 + 由浏览器按 DPR 和布局宽度自选：

<img src="photo-780.webp"
     srcset="photo-480.webp 480w, photo-780.webp 780w, photo-1024.webp 1024w"
     sizes="(max-width: 700px) 46vw, 320px"
     width="1024" height="1536" loading="lazy" decoding="async">

拿我们的十张首页精选实测，WebP q90 下各档位是这个量级：

档位十张合计单张均值相对现状532KB/s 下耗时适用图位
PNG 现状（1024 源）19.12 MB1958 KB1.0×36.8 s我们现在就这样
WebP q90 480w0.30 MB30 KB61.7×0.6 s瀑布流缩略、两列网格
WebP q90 640w0.49 MB50 KB37.2×0.9 sDPR2 小图位
WebP q90 780w0.69 MB71 KB26.3×1.3 s手机全宽 @DPR2
WebP q90 1024w（源）1.84 MB188 KB9.9×3.5 s详情大图、@DPR3

但这里有个反直觉的结论，必须说清楚：不要一刀切降分辨率。我按「手机真机观看尺寸 780 物理像素」做了画质比对：

方案十张合计PSNR 均值最差单张判读
WebP q92 全分辨率2.17 MB44.1 dB40.5 dB余量充足
WebP q90 全分辨率1.84 MB43.2 dB40.0 dB肉眼不可辨
WebP q92 @7800.81 MB40.2 dB34.9 dB仍可接受，但余量明显变薄
WebP q90 @7800.69 MB39.4 dB34.7 dBDPR3 屏上会看出偏软
WebP q85 @7800.50 MB37.9 dB33.9 dB开始有涂抹感

换句话说：降级是要拿画质换的，而且账面上不算便宜——降分辨率带来的收益是把 1.84 MB 再压到 0.69 MB，但画质余量从 43 dB 掉到 39 dB。真正的大头是第 2 层（19 MB → 1.84 MB），不是第 3 层。

所以正确姿势不是「全部替换成小图」，而是「分场景给」：列表 / 瀑布流 / 网格只给 480–780 档，点开看的大图给 1024 全档。这同时解决了另外一个隐性缺陷——我们现在没有缩略图概念，列表和查看器共用同一份 2 MB 文件。

本机实测：Pillow 12.3 + NumPy。所有方案统一呈现到 780 物理像素后与原图在同尺寸下的最佳渲染逐像素比 PSNR；耗时按服务器实测 532 KB/s 估算。
第 4 层 · 占位，消灭空白最高收益我们：未做

这是「初开全白」唯一的正解——图没到之前，先给一个内联在 HTML 里、零额外请求的模糊轮廓。业界四种成熟做法：

技术每张开销是否需要 JS 解码代表使用者判读
主色调约 4 B否Pinterest 风格最低成本消灭「纯白」，但无形无构图
BlurHash约 28 B是（约 1–2 ms）Mastodon、Signal经典，不带 alpha 与宽高比
ThumbHash25–35 B是（约 1–2 ms）新一代默认推荐比 BlurHash 更准，且自带宽高比与透明度
LQIP（极小图 data URI）200–800 B否（纯 CSS 放大）medium 风格老做法实现最简单，体积最贵

我们的素材实测：20px 长边的 WebP 占位图（base64 内联）平均 190 字节 / 张，十张合计不到 1.9 KB。按 BlurHash / ThumbHash 只会更小。用不到 2 KB 换掉「开屏全白」，是这一整套里性价比最高的一笔。

顺带：CSS 的 filter: blur() 只会作用在那张极小的占位图上，不要加在大图本身，低端机会掉帧。

来源：media-delivery / w3tweaks / pixotter 的占位技术对照；体积为本机实测。
第 5 层 · 加载数量与优先级打磨项
  • 每张 img 都写 width / height——让浏览器在解码前就知道比例。我们已做（首页精选瀑布流的 <img width height> 是合规的）。
  • LCP 图加 fetchpriority="high" + 不要 lazy。浏览器视口内图片默认 Low，布局结束后才提升——这个提升本身是滞后的。基线在 2024 年就地稳固（Chrome 101 / Safari 17.2 / Firefox 132），老浏览器直接忽略，零副作用。
  • 其余图 lazy + decoding="async"，避开主线程解码阻塞。
  • 别让首屏一次抓十张——减少并发大图数量本身就是带宽治理。
来源：MDN / web.dev Fetch Priority API。

关于「给 API 加优先级就能不被图片压后」——这条路走不通，别抱期望。 fetch() 在 Chrome 里默认已经是 High，没有提升空间；图片虽然默认 Low，但布局完成后视口内的图会被提升到 High，且 Chrome 117 起前 5 张大图会直接抬到 Medium 并允许并行取两张。所以现象的根因是「大图太多 + HTTP/1.1 只有 6 条连接」，不是优先级没调。真解决办法是下面 Part 03 的三条。

Part 02视频：业界的四条铁律

先说好消息——对照业界标准，我们的视频做对了两条：

业界做法我们
poster 首帧封面必须有，压缩到几十 KB有 poster（116 KB）
+faststart：把 moov 元数据移到文件头，实现边下边播已验证：三个 mp4 顶层顺序都是 ftyp → moov → mdat，元数据在文件首部

还差两条：

① 容器比例必须来自真实数据，不能写死

现在 views.css 里写死了 9/16（竖屏），拍横屏的内容就被硬塞进竖框再 cover 裁切，这就是你看到的变形。业界做法是 把宽高当成数据，和图片一样随接口下发，第一帧就用真实比例占好位置：

<div class="vinner" style="aspect-ratio: 1920 / 1080">
  <video poster="…" preload="none" playsinline></video>
</div>

我们后端 probeVideo() 早已用 ffprobe 读到了宽高，只是没落库也没下发——而同一个 /api/home 里，图片的 featured 字段是有 w/h/ratio 的。这是一处明显的口径遗漏。

② 大数据按需加载，不要预取

  • preload="none" 起手，滚动进视口或用户点击后再给 src（IntersectionObserver）。业界默认就是这个——preload="metadata" 已经会比预期多下载一段，auto 基本不该出现。
  • <video loading="lazy"> 现在也能自动懒掉 poster 和数据。
  • 自动循环的轻量背景视频，行业共识控制在 2–5 MB 以内。我们首页那个 20 MB 的主视频，无论其它优化做到什么程度，它都仍是首屏最重的单项。
  • 长视频才需要 HLS / DASH 自适应码率 + CDN 分片。对我们属于以后再说
来源：web.dev《Lazy loading video》、insync 的 ffmpeg 管线实践。

Part 03导航点了没反应：业界的三条解法

这一项不是 JS 崩溃。本质是「等待期间没有任何可见变化」。成熟框架对此的答案是同一句话：让「过渡状态」成为一个渲染出来的东西，而不是一段沉默。

① 骨架屏必须是「立即显示」的，不是「加载完再显示」

Next.js App Router 把这件事做成了框架默认约定——路由目录下放一个 loading.tsx，它被自动包进 Suspense 边界，点击的瞬间先渲染 skeleton 换掉旧页面，数据到了再替换。官方文档明确的好处里就有：「即时导航与视觉反馈」「过渡可被打断」「不必等整段内容加载完」。

我们现在的架构是 await route.view(shell) 的离屏渲染——取数期间 DOM 一个字都不动，好处是不白屏，代价就是你说的「点了没反应」。

② 并行请求，别串行瀑布

这是最朴素的业界共识：两个互不依赖的请求不要写成 await a; await b。

// 瀑布：第二轮必须等第一轮
const cols = await getCollections()
const counts = await Promise.all(cols.map(getCount))   // 第二轮才开始

// 并行：两个请求同时在飞
const [cols, counts] = await Promise.all([getCollections(), getCountAll()])

我们 collection 视图正好是这种两轮串行。

③ 避免 API 和图片抢同一批连接

这一条是「HTTP/1.1 + 没有 HTTPS」的专属问题，业界早已不在这个处境里，但我们可以对症：

  • HTTP/2 / HTTP/3 多路复用——业界常态，直接消除队头阻塞。我们需要域名 + 证书后才能有
  • 关键数据在应用启动时就预热，不等路由触发再去请求。
  • 把 API 挪到独立源（不同端口或子域）——浏览器的连接池按 scheme + host + port 划分，不同端口就是另一个池子，额外 6 条连接，图片再多也压不到 API 头上。这是 HTTP/1.1 时代的经典手段，今天仍然是零成本立刻可用的解法。

Part 05对我上一份设计稿的复盘

既然放一边了，就直接说清楚它对在哪、漏在哪。

设计稿条目结论说明
上传时处理，不在访问时压缩对符合业界共识
保留原图做底稿对出印刷品、后续重压都靠它
WebP q90–q92对实测 q90 全分辨率 43.2 dB、最差 40.0 dB，稳在肉眼不可辨区间
排除 AVIF对微信场景支持率不稳；编码成本不划算
内联模糊占位图对实测 190 B / 张
视频宽高入库并下发对ffprobe 已有数据
两轮请求合并、加骨架屏对与框架官方推荐一致
只交付单一尺寸的展示图漏了缺 srcset 分级，也没区分「列表缩略」与「点开大图」两级
未涉及加载优先级与连接竞争漏了缺 API 与静态分流的低成本解法
CDN 排在最后「以后再说」定位偏了它是收益最大的一层，只是恰好被备案卡住——应当标为「已排期，等待备案」，而不是「可选优化」
未做 URL 抽象漏了将来切 CDN 时全站图片地址要统一走一个函数，现在埋进去成本几乎为零

顺带上一份长期隐患：素材里 murpboe2-4608157c.png 实际是 379 字节的 HTML 错误页，却被当成 PNG 存下来、并以 image/png 返回 200。目前没有接口引用它，不影响线上，但它说明上传链路曾经放过不该放的东西。任何一道「真解码校验」都能拦住它。

Part 06建议的推进顺序（待确认）

  1. 素材加工链——WebP 展示档 + 480/780 两个缩略档 + 几十字节占位 hash，一次跑完。不动原图，随时回滚。
  2. URL 抽象层——所有图片地址收敛到一个函数里去拼，为将来切 CDN 做准备，此刻成本几乎为零。
  3. 视频宽高入库下发 + CSS 用真实比例——改动集中在下发与消费两端。
  4. 交互反馈——骨架屏 + 请求并行化 + API 独立端口，与前两项无耦合。
  5. 上传流水线接入同一套加工——防止新素材复发，前四项验证通过再动。
  6. 域名备案一下来——立刻把图迁进 COS + CDN + 数据万象，那时候今天的加工逻辑可以直接改由 URL 参数在云端完成，本地流水线可以整体退役。
