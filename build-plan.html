SECTION 00

定下的五件事

你说了「域名和备案不急，先把项目做起来」—— 这份文档里所有事都不依赖域名，本地就能全流程跑通。

决策结论依据
H5 前台 原生 ES modules · 零框架 · 零依赖 · 零构建 7 个页面、结构固定、访客全在微信里 —— 性能与兼容性优先。现有 demo 已用 850 行零构建跑通 6 页 + 查看器 + 转场，这是一手证据
管理后台 Vue 3 + Vite + TS + Element Plus 表单密集、六段编辑、多图拖拽排序 —— 开发效率优先。这里用框架省 300–500 行，是实打实的账
后端 Node 22 + Fastify 5 + TS · 常驻约 80 MB 1.6 GB 内存是唯一硬约束：Java 329 MB vs Node 80 MB —— 4 倍差，在这里是决定性的
部署形态 宿主机 Nginx（443 · TLS + 两份静态 + 反代 /api）＋ 单一 mua-api 容器 比上一版简化一层：不再单独跑 mua-web 容器，省一个组件、一层跳转、一份配置
数据来源 全部走 DB + API，data/albums.js 退役 v6 的 IA 与旧数据结构不兼容（详见第 08 节），不是改名字能解决的 —— 但这一条与框架选择无关
为什么现在可以开工：唯一的长关键路径是域名备案（1–3 周），但它只卡上线，不卡开发。 前台 localhost 跑、后端 localhost 跑、数据库本机跑，图片先用现成的 10 张占位图。 域名下来后，只剩「装 Nginx + 签证书 + 指域名」半天的事。
SECTION 01

技术栈定案

同一个站点，前后两半的需求正好相反，所以用两套栈。每一行左边是选型，右边是它对应的理由 —— 没有一条是为了「技术先进」选的。

H5 前台 · 原生，零构建

项选型为什么是它
框架无7 个页面、结构固定（六段是写死的枚举）。框架在这里主要解决「数据→视图同步」，而我们的数据规模是一次请求几十条记录
语言JS + JSDoc // @ts-check零构建下仍能拿到字段级类型提示与拼写检查（VS Code 原生支持），补掉「没有 TS」这个真实短板
组织方式多文件 ES modules按页面 / 组件拆文件，代替「一个 main.js 拼 1000 行模板字符串」
路由自写 history 路由（约 40 行）分享出去的链接要是 /album/w1 而不是 #/album/w1。实现是 pushState + popstate + 拦截站内 <a>，配合 Nginx try_files 兜底
运行时依赖0 个没有 node_modules、没有版本升级、没有依赖漏洞、没有构建等待
样式原生 CSS（变量 + 分层）双主题 = 换根 class（.twe / .tcn）；玻璃三档 = 三组 CSS 变量。这两件事本来就该在 CSS 里做
动效CSS + IntersectionObserver不上 GSAP。光斑漂移、扫光、呼吸、走马灯、滚动入场 —— 设计稿里全部动效原生就能做
i18n不做 locale 切换设计稿里的英文是「9px 疏排点缀」，属于版式的一部分。DB 存 *_cn / *_en 双字段，同屏并列渲染
体积预估≈ 25 KB 未压缩 / ≈ 10 KB gzip对微信弱网最友好。对比：Vue + router 约 +45 KB gzip，而一页图片就是 1–3 MB
为什么前台不上 Vue（虽然 +45KB 相对图片量级不大）。 真正的理由不是体积，是这个站没有任何需要框架的场景：无跨页共享状态、无复杂表单、无长列表虚拟化、无实时更新。 引入框架只买到「模板写起来舒服一点」，代价是构建链路 + 依赖管理 + 版本升级 + 服务器不能 build（必须本地 build 传 dist）。 一个内容每年更新几次的展示站，不值得长期背上这些。
一个必须实测才知道的项：Android 微信 X5 对 ES modules 的支持。 我不能凭记忆断言它的支持矩阵，所以把它当成开工第一件要验证的事： M1 跑通后立刻在真机微信里打开，测四件事 —— ① <script type="module"> 是否执行；② 可选链 ?. / 空值合并 ??； ③ backdrop-filter 的降级是否生效；④ aspect-ratio 是否按预期算高。

最坏情况也不改架构：若 ①② 不通过，加一步 esbuild 把多文件合成单文件（单二进制、无依赖树、构建 <100ms）， 或把语法基线降到 ES2017。这些全是可降级项，不是架构风险。

管理后台 · Vue 3

项选型为什么是它
框架Vue 3 + Vite + TypeScript你熟；双向绑定正好对上表单密集的场景
UI 库Element Plus表格、表单校验、抽屉、上传、消息提示全是现成的；只进 /admin，不污染前台
拖拽排序原生 HTML5 drag & drop 或轻量 sortable多图排序是后台最核心的交互，必须有拖拽
构建本地 npm run build → 传 dist服务器 2 核 1.6 GB 不 build（本地都踩过 OOM）
鉴权单账号密码 + JWT（7 天）只有一个人用。不做注册、不做找回密码、不做多用户、不做权限树

后端 · Node + Fastify

项选型为什么是它
运行时Node 22（容器内自带）宿主机不需要装 Node —— 镜像里带，宿主机保持干净
框架Fastify 5常驻约 80 MB；内置 JSON Schema 校验与序列化，比 Express 快一个量级
数据库驱动mysql2（连接池）不引 ORM / Prisma：Prisma 要额外跑二进制 engine，在 1.6 GB 机器上是负收益。表一共 8 张，手写 SQL 更可控
迁移自写 runner（约 40 行）migrations/*.sql + 一张 _migrations 表，按文件名顺序执行、已执行的跳过。不引重型迁移框架
类型TypeScript，types.ts 作为 API 契约后台直接 import type 复用，接口字段改名时编译期就报错
密码bcrypt 哈希存库账号密码写在 .env（权限 600，不进 git）
日志pino（Fastify 内置）容器日志已被 log-opts 限制在 20m×3，不会吃盘

数据与图片

项选型为什么是它
数据库复用 sanhe-mysql · 新建库 mua_portfolio零新增依赖；独立 database + 独立账号，物理上碰不到 sanhe_aquatic
连接方式加入 sanhe 的 Docker 网络，用容器名 sanhe-mysql:3306不依赖宿主端口映射（不确定它有没有映射），容器名解析最稳
字符集utf8mb4 / utf8mb4_0900_ai_ci要存繁体「予時妍」与 emoji
图片COS + CDN + 数据万象转码 / WebP / EXIF 纠向 / 视频截帧全托管。照片不落服务器磁盘（400 张 ≈ 0.6 元/月）
上传STS 临时凭证，浏览器直传 COS不过业务服务器 —— 2 核 1.6 GB 的机器经不起图片流
尺寸变体不预生成，走 COS 处理样式实时出图存原图 key + 宽高，前端按样式名拼 URL
本地开发先用 assets/img/ 那 10 张占位图DB 里存的路径与 COS key 同构 → 上线时只换 base URL，代码零改动
唯一的版本红线：不打「latest」标签上生产。镜像与依赖在 package.json / Dockerfile 里锁版本， 否则半年后重建镜像会拉到不兼容的主版本，而那时你已经不记得当初装的是什么了。

SECTION 03

数据模型

8 张表。六段叙事用枚举落库，不用自由文本 —— 这样前端能固定渲染那 6 枚流程胶囊，同时标题文案仍可由后台覆盖。

表行数级作用与关键字段
album10 – 50 一本册 = 一场婚礼里的一种风格。字段：slug · title_cn/en · style(western/chinese) · category(wedding/engagement/maternity) · ordinal_label（Ⅰ / 壹）· cover_key · cover_len_ratio（4:5）· sort · published · video_key/poster/duration（一期只留字段）
album_section60 – 300 六段叙事的载体。字段：album_id · kind 枚举 · title_cn/en · desc_cn/en · layout(auto/single/duo/grid/strip) · max_visible · sort
photo400+ 字段：section_id · cos_key · w · h · ratio · orientation(portrait/landscape) · caption_cn/en · sort
collection2 两条：西式浪漫、新中式。字段：slug · style · big_cn（封面大字）· tagline_cn/en · vslip_cn（竖排绢签文案）· cover_key · strips_json（右下三张小图）· palette_cn · sort
gallery / gallery_photo2 / n 订婚宴、孕亲照两个平铺图集。结构与 album 解耦（它们没有六段），刻意不复用 —— 硬塞进 album 会让六段枚举被迫出现空值
site_setting单行 品牌名 / 副标 / 标语 / 关于页 bio / 三组统计数字 / 流程四步 / 微信号 / 二维码 key / 社交分享图 key。全部配置化，改文案不用碰代码
admin_user1 单账号：username · password_hash · last_login_at
_migrationsn 迁移 runner 自己的账本：记录已执行的文件名与校验和

-- album_section.kind 枚举。西式与新中式共用同一套 kind，
-- 差异只在标题文案与呈现皮肤（罗马数字 Ⅰ–Ⅵ / 汉字 壹–陆）

被删掉的那一段：迎宾造型。现有 demo 的 data/albums.js 里每册有 5 个场景 + 2 个特写， 其中包含「迎宾造型」。设计稿 v6 拍板的是六段，没有迎宾。 这意味着旧数据里那 9 处 yingbin 记录会被丢弃 —— 已确认（2026-10-02）：这是本轮唯一一处删功能，不是改名。

与旧数据的对照

维度现有 demo · data/albums.js新 · DB 模型

SECTION 04

接口清单

前台 6 个只读接口（无鉴权、可被 CDN 缓存），后台 11 个（JWT）。没有 REST 教条，只按页面需要聚合。

前台 · 公开只读

方法路径服务页面返回
GET/api/site/about · 全局品牌、副标、标语、bio、统计、流程、联系方式、分享图
GET/api/home/hero 图与标签、三类入口、走马灯词、署名条
GET/api/collections/collection两张封面卡（西式在前）
GET/api/albums?style=/style/*册列表：slug、序号、封面、标题、meta、首图三连
GET/api/albums/:slug/album/*一次给全：册信息 + 六段 + 每段照片数组（含 w/h/orientation）
GET/api/galleries/:slug/gallery/*图集的照片数组
为什么详情页「一次给全」而不是分段懒加载。一本册最多 6 段 × 6 张 = 36 条记录， 去掉 blob 只有几 KB JSON。一次请求换来的是：查看器可以直接复用同一份数据（零请求）、 切段不闪、返回不白屏。分段加载在这里是纯粹的复杂度。

后台 · JWT

方法路径作用
POST/api/admin/login单账号密码 → JWT（有效期 7 天）
GET/api/admin/albums册列表（含草稿）
POST/api/admin/albums新建册（选风格 + 类别 → 自动初始化六段空壳）
PUT/api/admin/albums/:id改册信息 / 封面 / 排序 / 发布状态
DELETE/api/admin/albums/:id删册（软删，deleted_at）
PUT/api/admin/sections/:id改段落文案 / 布局覆盖 / max_visible
POST/api/admin/sections/:id/photos登记已直传的 COS key（含 w/h），落库
PUT/api/admin/sections/:id/photos/order批量重排（一次提交整个顺序数组）
DELETE/api/admin/photos/:id删图（同时按 key 删 COS 对象）
POST/api/admin/cos/sts签发上传用 STS 临时凭证（最小权限，仅本桶指定前缀）
GET / PUT/api/admin/settings站点配置读写
一个容易被忽略但会省掉很多事的约定：photo 的宽高由前端在上传成功后回传。 浏览器在直传前就能用 createImageBitmap 读出 width/height， 连同 COS key 一起进 POST .../photos。这样后端完全不需要读取图片元数据 —— 不用装 sharp、不用拉 COS SDK 做 HEAD、不用处理 EXIF。多图布局的自动选型全由这两个数字驱动。

两个必须提前处理的接口细节

① 复用 sanhe-mysql 不能靠宿主端口。我们不确定 sanhe 的 compose 有没有把 3306 映射到宿主。 正确做法：把 mua-api 挂进 sanhe 已有的 Docker 网络（docker network ls 查出名字， compose 里写 networks: { sanhe_default: { external: true } }），然后用容器名 sanhe-mysql:3306 连接。 这样既不依赖端口映射，也不占宿主端口。M2 建库前第一件事就是核这个名字。

② 容器日志上限要一起设上。新容器直接在 compose 里写 logging.options.max-size: 20m / max-file: 3，避免将来这台的 json-file 无限增长。 这条只影响 mua-api 自己，不需要重启 docker daemon —— 与 sanhe 那两个待办（全局 log-opts、live-restore）分开处理，不制造任何中断。
