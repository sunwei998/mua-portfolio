更正 · 上一版报告里的「Docker Hub 拉不到镜像」是误判。 当时我用 curl 直连 registry-1.docker.io，它被 DNS 解析到 IPv6 污染地址、服务器无 IPv6 出口， 于是超时 —— 但 curl 根本不读 docker 的镜像源配置，这个探测从方法上就是错的。 真实情况：服务器上 /etc/docker/daemon.json 早就配好了腾讯云内网源， 实测 docker pull hello-world 0.98 秒完成，部署第一步不存在障碍。
更正 2 · 上一版报告里的「443 未放行」同样是误判（用户当场指出）。 控制台防火墙里 HTTPS 443 → 允许 一直在列。原因：腾讯云轻量的「防火墙」等同安全组、位于云平台层， 实例内部看不到它；我上机只看到 iptables INPUT 里一条 YJ-FIREWALL-INPUT 跳转， 没展开链、也没做外网探测，就臆断了"未放行"。

两次误判是同一类病根：拿一个看不到全貌的本地视角，去推断一个由外部控制的事实。 正确姿势 —— 「能不能连上」这类问题，只能在外部实测：nc -z -v <IP> <port>， refused = 已放行（包到达内核）／timed out = 未放行（SYN 被丢弃），并用一个已知未放行的端口做对照。
发现 2 · 有一个服务白占内存（已处理 ✅）。fwupd 是 Ubuntu 的固件更新守护进程， 在云服务器上毫无用处（没有物理固件要更新）。已 stop + disable + mask， 进程退出后可用内存从 615 MB 涨到 791 MB（+176 MB），比我们要新增的两个容器加起来还多。
发现 3 · 不能手搓 sanhe 的 compose。/opt/sanhe/.env 不存在， 而 compose 里 MYSQL_ROOT_PASSWORD 是必填项。直接跑 docker compose up 会启动失败。 这个文件由 update.sh 生成 —— 所以 sanhe 的一切操作都必须走它自己的 update.sh。

为什么不改 sanhe 的端口来腾出 80。技术上可行（compose 里 ${HTTP_PORT:-80} 是可配的）， 但那要重建 sanhe-web、会中断生产、而且 .env 不在手边，风险不对称。 用 443 分流能拿到同样的结果，代价是零。唯一的功能损失是 http → https 自动跳转 —— 而微信里的链接本来都是 https，实际无感。
证书为什么要用免费 DV 而不是 certbot 自动续期。Let's Encrypt 的 HTTP-01 验证必须走 80 端口， 而 80 被 sanhe 占着 —— 除非动 sanhe，否则收不到验证请求。腾讯云免费 DV 走 DNS 验证，绕开这个死结。 代价是一年手动换一次。

02 · 无需操作 ✅（上一版判断有误）
Docker 镜像源已存在且可用
服务器原本就配好了 registry-mirrors = mirror.ccs.tencentyun.com。 本次用 systemctl reload docker（热重载，没有重启 daemon）验证生效， 实测 docker pull hello-world 0.98 秒。

教训：上一版用 curl 直连 registry-1.docker.io 判断"Docker 拉不到镜像"是错的 —— curl 不读 docker 的镜像源配置。系统文件也应用 sudo cat 读，普通用户 cat 因权限 640 会静默失败、被误判为"文件不存在"。
03 · 无需操作 ✅（上一版判断有误，用户已指出）
腾讯云 443 早已放行
控制台「防火墙」里 HTTPS (443) TCP 全部 IPv4 → 允许 一直在列。 外网实测证实：443 返回 Connection refused（SYN 到达内核、无服务监听 → 内核回 RST）， 而同样未放行的 8081 / 9999 返回 Operation timed out（SYN 被丢弃）。 refused 与 timeout 的区别，就是"放行"与"未放行"的铁证。
为什么我会判断错：腾讯云轻量的「防火墙」= 云平台层的安全组，实例内部完全看不到它。 我上机查 ufw（inactive）和 iptables -L INPUT（policy ACCEPT，只有一条 YJ-FIREWALL-INPUT 跳转），没有展开那条链、也没有做外网探测，就臆断了"443 未放行"。 这和上一版"Docker 拉不到镜像"是同一类错误：拿一个看不到全貌的本地视角，去推断一个由外部控制的事实。
还发现两个可选的优化项（不影响开工，要不要做你说）：
① 容器日志没有上限：daemon.json 里没设 log-opts，默认 json-file 会无限增长 —— 长期跑会把 32 GB 剩余磁盘慢慢吃掉。加 max-size: 20m / max-file: 3，需要重启 docker 才生效。
② live-restore 未开启：开启后重启 docker daemon 时容器不中断 —— 以后我们要动 daemon 就不会波及 sanhe。同样需要重启一次才生效。
这两条可以合并到未来某次必然要重启 docker 的窗口里一起做，不必单独制造一次中断。
