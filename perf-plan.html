这三个现象不是三个独立问题

它们有一条共同的因果链：超大 PNG 占满带宽 → HTTP/1.1 六并发被吃光 → API 请求排队 → 页面无响应。根治第一项，后两项会自动大幅缓解，但各有自己的独立根因，需要分别处理。

Part 02根因定位

现象一 · 图片加载慢、开头全空白

  • 照片被存成了 PNG。 PNG 是为图形设计的无损格式，存连续色调的照片时效率极低——同一张图 WebP 只需七分之一体积。
  • 上传时没有任何处理。 后端接收后直接落盘，既不转码也不生成缩略图。
  • 首屏图片拿不到懒加载保护。 loading="lazy" 只对视口外的图生效，精选区就在首屏，必然立即并发拉取。
  • 没有占位机制。 图没到之前 DOM 是真空的，所以你看到的是一片白。

注意：Nginx 这一侧的缓存与压缩配置全部正确——gzip 已生效、静态资源有 immutable 长缓存、Range 分片正常。问题出在素材本身和上传流程，不需要改 Nginx。

现象二 · 视频初始竖屏变形

  • 视频容器 CSS 写死了 aspect-ratio: 9/16（竖屏），横屏视频被塞进竖框，由 object-fit: cover 强行裁切——这就是你看到的变形。
  • 真实比例要等 loadedmetadata 事件才能写入，而该事件依赖元数据下载完成，慢网下要等很久。
  • 接口没有下发视频宽高。 /api/home 的 videos 字段只有 key 和 posterKey。对比之下，同一个 /api/home 接口的 featured 图片是有 w/h/ratio 的——设计时想到了图片，视频这块漏了。
  • 后端 probeVideo() 早已用 ffprobe 读到了宽高，只是没有落库也没有下发。

现象三 · 点了「作品」「联系」没反应 非 JS 崩溃

  • 路由采用离屏渲染：await 取数期间旧页面保持可见，DOM 一个字都不改。好处是不会白屏，代价是等待期完全静默。
  • collection 视图存在两轮串行等待——先拉系列列表，再并行拉各系列册数。
  • HTTP/1.1（没有 HTTPS 就没有 HTTP/2）下浏览器每域名仅 6 条并发，API 请求排在八张 PNG 后面慢慢等。
  • 等待期唯一的视觉反馈是顶部一条进度条，几乎察觉不到。

Part 03画质会不会下降

这是最关键的问题，用实测回答，不用感觉。

取首屏最大的一张（1024×1536，2.53MB），按手机真实观看条件比对——CSS 宽 390px、二倍屏即 780 物理像素，所有方案统一缩到这个尺寸后再与原图逐像素计算 PSNR。PSNR 达到 40dB 即为肉眼不可分辨。

方案体积缩小PSNR平均误差肉眼判断
PNG 现状2586 KB—99.0 dB0.00比对基准
WebP q95499 KB5.2×41.8 dB1.41不可分辨
WebP q90　推荐356 KB7.3×40.0 dB1.75不可分辨
WebP q85276 KB9.4×38.3 dB2.12极轻微
WebP q80229 KB11.3×37.0 dB2.43极轻微
JPEG q90427 KB6.1×39.0 dB1.87极轻微

结论：不会。 推荐档 WebP q90 的平均像素偏差是 1.75（灰度 0–255），折合 0.7%——远低于屏幕本身色差、环境光和观看距离能分辨的程度。更重要的是分辨率完全不变，1024×1536 一个像素都没减，只换了编码方式。这不是压缩，是去掉格式浪费。

考虑到这是作品集、你对画面要求高，我建议走保守档 q92：仍比现在小约 6 倍，但画质余量更足。也可以按你的判断用 q90。

Part 04根治设计

核心思路：访客访问时不做任何压缩，所有工作在上传那一刻完成。

P0 素材流水线（上传时处理一次）

后台接收文件后增加一道处理环节，产出三类文件：

  • 原始文件——移入归档区，不作为前台交付源。你将来出印刷品、做高清输出仍有底稿。按你的选择保留
  • WebP 展示版——尺寸维持原始分辨率，q90–q92。前台实际加载这份。
  • 模糊占位图——约 1KB 的极低分辨率版本。它随接口内联下发，图没到之前先显示模糊轮廓，直接消灭「开头全白」。

顺带解决一个隐患：处理环节第一步做真实解码校验。当前素材里已发现一个假图片——murpboe2-4608157c.png 实际是 379 字节的 HTML 错误页，却被存成 PNG 并以 image/png 返回 200。目前它没有被任何接口引用，属历史残留，但足以说明链路曾经出过问题。

JPEG 兜底：iOS 14+ 与微信 X5 均支持 WebP，但为极少数老环境保留一份 JPEG，由 <picture> 标签自动降级。AVIF 不予考虑——压缩率略好，但微信内置浏览器支持不稳。

P1 视频元信息补充

  • 后端已有 ffprobe 数据，补两个字段落库：video_width、video_height。
  • /api/home 的 videos 增加 w/h 下发，与图片字段口径对齐。
  • 前端用真实比例初始化容器宽高比——第一帧即正确构图，不再依赖 loadedmetadata。
  • CSS 默认值从写死的 9/16 改为：有元信息时用元信息，没有时才回退。

P1 交互反馈

  • collection 视图的两轮串行等待合并为一次并行请求。
  • 路由切换时立即给出明确反馈——骨架屏或当前区域的脉动占位，而不是只有一条几乎看不见的顶部进度条。
  • 图片进入视口的过程保留现有的淡入动效，配合占位图形成完整的加载叙事。

关于视频本身：当前 20MB 的主视频即使在优化后仍是首屏最重的单项。建议本次不动视频文件（它的封面图正常、也有 Range 分片，播放体验尚可），只修构图问题。等前端这一轮稳定后，再单独评估是否需要压制视频码率或改走 CDN。

Part 06执行顺序与风险

  1. 存量素材批处理（风险最低，立竿见影）。原图归档，失败可随时回滚。
  2. 视频宽高字段（一次迁移 + 少量代码）。已有 ffprobe 数据，改动集中在下发与消费两端。
  3. 交互反馈（纯前端）。与前两项无耦合。
  4. 上传流水线改造（防复发，改动最大）。前三项验证通过后再动。

唯一的真实成本：上传时每张图多花 1–3 秒做转码。按当前素材量，后台上传一张 2.5MB 的图约增加 2 秒等待——换来的是每位访客节省 30 秒以上。这笔账明显划算。
